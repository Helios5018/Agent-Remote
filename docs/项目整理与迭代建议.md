# 项目整理与迭代建议

**核心思路**：保留现有 Bun monorepo 和 cmux 适配边界，先统一文档入口、补齐关键行为验证，再按职责拆分前端状态和服务端业务逻辑，最后迭代远程使用体验。

**改动范围**：建议涉及 README、docs、AGENTS.md、前端 pages/stores/styles、服务端 api/state/realtime、workspace 依赖与测试配置。本次仅新增本报告，未实施代码重构或删除。

**影响评估**：文档整理风险低；状态与实时链路拆分可能影响订阅、未读、滚动和刷新时序，必须分批进行。历史文档移动需要同步引用；缓存与审计保留策略需要明确期限。既有 9 个未提交修改保留，未发布或重启服务。

审查日期：2026-09-05。依据为当前工作区源码（包含未提交修改）、配置、文档及现有测试，不代表线上验收。

## 1. 总体判断

顶层结构已经清楚：`apps/server`、`apps/web`、`packages/protocol`、`packages/shared` 的边界适合当前规模。`CmuxClient` 接口、Fake 客户端、运行时无关的 Hono app 和 RealtimeHub 都值得保留。当前问题主要是局部职责集中、文档混合使用说明与历史经验，以及生命周期行为缺少前端集成测试。

无需为了整理新增微服务、复杂插件系统或更多共享包。先让每个文件负责一件可描述的事情。

## 4. 优先优化的代码问题

以下除测试结果外均为源码审查结论；用户可见影响尚待针对性测试或真机复现。

### P1：实时与状态正确性

1. **普通 shell 查看刷新可能只有 8 秒。** `realtime/poller.ts` 的 finally 通过 `engine.get()` 决定下次读取；非 Agent surface 没有 state，落入 idle 间隔，即使仍有人查看。应先按 isViewed 决定间隔，并补非 Agent 查看场景测试。
2. **两套 revision 的边界不一致。** Poller 已明确网格与纯文本编号不能混用，但 `api/surfaces.ts` 的 GET grid 仍把 grid.revision 传给 `engine.applyOutput()`。应拆开画面版本与状态活动信号，验证打开/离开会话不会造成虚假的输出变化。
3. **无 Hook 会话的静止推断需要验证。** 前台网格 revision 不变时直接 return，不再调用 applyOutput；engine.tick 只处理 stale 规则。需要验证持续查看时 WORKING 能否按预期收敛为已回复/空闲。
4. **重连生命周期不完整。** `useRealtime.ts` 的旧 onclose 闭包可能保留 enabled=true，在 effect cleanup 之后再次安排重连；已有指数退避，但没有应用层 ping/pong 超时检测。建议使用连接代次或 disposed 标记取消旧回调，按需要补心跳与重同步。
5. **断线降级覆盖不足。** AppStore 的降级轮询只刷新 inbox，不刷新正在查看的 grid；连接恢复仅恢复订阅，服务端建立连接只发 hello。应在重连后主动拉取状态和当前画面，并明确断线期间画面的新鲜度。
6. **分组与统计存在局部不一致窗口。** patchAgent 只替换已有 Agent，没有重算分组和 summary，也不会插入新 Agent；部分状态变更依赖后续整表广播纠正。应集中归一化数据和派生统计，测试 mark-read 等只有状态事件的路径。

### P1：失败处理和可诊断性

- `state/db.ts` 捕获数据库打开异常后可能静默退化为无持久化实现。建议真实运行时明确报错或显式提示降级；测试通过依赖注入使用内存模式。否则 PIN、会话与审计持久化能力可能悄悄消失。
- 新建 surface 后通过固定 150ms 等待启动 Agent；启动步骤失败时 surface 可能已创建，但返回整体错误。拆服务时返回明确的部分成功状态，避免用户重试又新建 tab。
- `/api/health` 目前只表示 HTTP 服务活着。增加登录后可见的诊断信息：最近拓扑成功时间、读取耗时、Hook 最后事件、存储模式与最近错误；不展示密钥或终端正文。

### P2：性能和长期运行

- AppStore 单一 Context 包含 grids；任意网格更新都会更新 Context value，影响其他消费者，操作方法也随 value 重建。分离高频数据订阅和稳定 actions，再用实际渲染耗时验证收益。
- 首页 4 秒拉 tree，服务端 2 秒刷新拓扑。可增加 `tree.changed` 消息并保留断线兜底，减少重复请求；继续保留 CLI 的 TTL 与 single-flight。
- 统一 surface 关闭后的清理协议：前端缓存、Poller 的 nextDueAt/gridRevisions、engine 的 sessionIndex，以及 CLI trackers。当前通过 Web 关闭已有部分清理，但外部关闭与长时间访问多个会话需要统一处理；登出还应清掉 contents。
- audit_log 查询有 LIMIT，但没有保留策略。按期限或条数清理，并测试边界，避免长期运行无限增长。
- Service Worker 缓存名固定，成功请求的静态资源持续入缓存，旧 hash 资源未按版本淘汰；失败的 JS/CSS 请求也会回退 index.html。增加版本清理并只对页面导航使用 HTML 回退。
- 先测 CLI 读取次数、读取延迟、WS 流量和前端渲染，再决定是否做网格差量传输或虚拟列表。

## 5. 工程整理与验证

- `apps/web/package.json` 使用了 `@car/protocol`、`@car/shared`，但未声明 workspace 依赖；当前靠 alias/root 配置工作。显式声明依赖，减少隐式耦合。
- 根包和子包存在重复运行时依赖声明。按实际导入方归属整理，但先验证 Bun 安装、根入口运行和构建，不能凭重复就删除。
- tsconfig 的 include 未包含 `apps/web/test`；纳入类型检查或为测试单独配置，避免“全量类型检查”遗漏前端测试。
- 当前前端测试主要验证从组件导出的纯函数，缺少组件生命周期与浏览器交互测试。优先补断网重连、发送失败保留草稿、切换 surface、历史滚动、关闭最后一个 tab 等关键行为。
- 将 protocol/shared 的纯函数测试逐步归回所属 package，服务端 API 集成测试仍保留在 server。
- 仓库当前没有受版本控制的 CI 配置；建议在 GitLab 配置 frozen-lockfile 安装、类型检查、测试、构建四个门禁。远端是否另有外部 CI 未核验。
- 不在 README 手写会变动的测试数；现役说明写验证命令，历史报告记录日期、版本和当时结果。

## 6. 产品迭代优先级

| 顺序 | 迭代方向 | 用户价值与边界 |
|---|---|---|
| 1 | 可信状态 | 标明状态来自 Hook 还是输出推断、最近更新时间、断线/过期原因，降低“到底卡没卡”的判断成本 |
| 2 | 连续输入体验 | 在已有发送失败保留内容的基础上，按 surface 保存会话内草稿，完善切换与重连体验；跨刷新保存应单独决定存储与清除策略 |
| 3 | 快速处理需要你 | 首页保留结构树，增加“只看需要你”和“下一个待处理”；直接复用现有 attention 状态 |
| 4 | 接入诊断 | 在一个页面查看各 Agent Hook 是否接通、上次事件和 cmux 可用性；Pi 的精确 Hook 接入作为后续独立任务 |
| 5 | 关注与提醒 | workspace/surface 置顶；再做可选完成/待批准通知、去重与静默时段，具体渠道另行设计 |
| 6 | 更大范围管理 | 真实需求出现后再做 Project 聚合、多设备控制冲突提示、任务队列；多用户、Relay 和完整终端模拟器不作为当前整理前提 |

## 7. 分批实施与验收

1. **文档和工程基线**：拆 README、归档历史、同步文档引用、完善依赖声明和类型检查范围。验收：新接手者能找到唯一启动/架构/运维入口，现有测试和构建通过。
2. **正确性修复**：先为上述 P1 风险补行为测试，再修复实时、revision 和错误反馈。验收：普通 shell 与 Agent 查看刷新符合策略；退出不残留连接；无 Hook 静止推断正确；断线恢复到最新状态。
3. **结构拆分**：按 workspace → session → Store → services → engine 的顺序，小批拆分，每批保持行为一致。验收：已有门禁通过，关键浏览器流程通过。
4. **体验迭代**：先做草稿、可信状态和待处理导航，再根据使用反馈选择通知、Pi Hook 或 Project 聚合。

不建议在一个提交中同时移动所有文件、重写状态流并添加新功能。
